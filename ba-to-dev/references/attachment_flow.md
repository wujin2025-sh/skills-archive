# 附件处理细则（ba-to-dev 引用）

> 本文件是 `SKILL.md` P0#28「附件处理」的完整执行细则。需求原文含**附件**（配图、Word/PDF 设计文档、接口/字段清单等）时执行；无附件不加载。
> 主文件只保留 P0#28 摘要，本文件保留「什么时候拉、怎么判、怎么转、怎么消化」。

---

## 一、附件识别与自动拉取

### 1. 判断是否有附件
- 从 `kjptai` MCP 返回的需求数据检查附件字段（`attachments` / `fileList` / `technologyFileList` / `attachmentLinks` 任一非空即有附件）。
- 无附件 → 跳过本细则，按文本继续分析。
- 有附件 → 继续拉取。

### 2. 自动拉取（强制，默认动作）
- 对每个附件用其 `downloadUrl`（形如 `https://fintech.gtht.com.cn/download?id=<附件ID>` 或 `.../api/message-service/attFile/downloadFile?id=xxx`）**HTTP GET 下载原文件**。
- 下载地址来自 kjptai MCP 返回，无鉴权可直接访问，属合法流程（**不禁爬虫立场**：平台下载地址本身可直拉，非绕过登录抓取）。
- 下载成功 → 进入第二步「分类与整理」。
- 下载失败 → 提示用户手动放入，**基于已有文本继续，不中断流程**。

## 二、附件分类与整理

### 1. 无效/冗余附件判定（强制，先判再消化）
- 解析附件正文，与 in-page「一、需求背景 / 二、需求内容」比对：
  - **正文与需求内容重复度高、无 in-page 之外新规格** → 无效/冗余附件：不做深度消化，仅在文档标注「附件《xxx》内容与需求正文一致，为冗余附件，已忽略」。
  - **含需求正文之外的新规格**（组件定义、功能清单、字段、接口、流程、规则、改造方案）→ 有效附件，进入深度消化。
- **判定原则**：重复度高→无效；有 in-page 未出现的新信息→有效；不确定先解析全文再判，不提前臆断。

### 2. Word 附件统一转 md（强制，原文件保留）
- 对**有效**附件中的 `.docx`/`.doc` **必须转 Markdown**（工具：`scripts/docx2md.py`，存于 ba-to-dev 工具目录）：
  ```bash
  /usr/local/bin/python3 <ba-to-dev>/scripts/docx2md.py <附件.docx> <附件.md>
  ```
- 转换目的：① 便于 AI 深度消化（见第四步）；② Obsidian 可直接预览；③ **文中图片以 base64 内嵌进 md**（`data:image/...;base64,`），供 AI 分析与观测，md 自包含、任意渲染器（含 Obsidian）可显示。
- **保留**：标题层级与章节编号、merge 感知表格（合并单元格不重复复制）、base64 内嵌图片。
- 落地：原 `.docx` 保留在附件目录；转换产物保存为 `<需求编号>-<附件描述>.md`。
- 非 Word（pdf/xlsx/txt 等）按各自方式解析/Read 读取，不强转 md。

## 三、附件落地与命名
- 原文件落**需求文档同目录的 `附件/` 子目录**（`/100_Projects/需求分析/<需求名>/附件/` 或 `png/` 视类型）。
- 有效 Word 的 md 版落附件目录。
- 无效/冗余附件原文件仍保留（留凭证），不生成 md / 不深度消化。
- 落地后在文档标注「本需求附件《xxx》已落地到 附件/」。

## 四、附件内容纳入分析（深度消化）

### 1. 提取规格
- 对**有效附件**，用 md/解析内容提取：组件定义、功能清单、字段、接口（功能号）、流程、规则；纳入「三、技术实现」结构化重组；提取接口关键字供「接口查询」SKILL 核对。

### 2. 图片消化（强制，留痕）
- **架构图、时序图、流程图、字段/页面截图**往往承载文字之外的规格（拓扑、组件、流程节点、数据方向、边界规则）。
- **⚠️ 本技能模型不支持读图**（read 图片返回但不解析像素内容）：凡含业务配置信息的图，**严禁把看图猜测的配置项当作实证**写入文档；须在第四章审计「待人工核对」标注需人工查看，或遵循 P0#28「不可读外置」原则。
- 逐图核对后**无论有无新信息都须留痕**：确认无新信息 → 在「一、技术实现」备注「已逐图核对，图片信息已并入上文」；含未知配置 → 标「待人工核对」。
- 配图作为需求附件**嵌入文档原文区末尾**（Obsidian `![[png/图名.png]]`），不污染一、二章原文字（遵 P0#28）。

### 3. 内容采用规则
- 若 in-page「二、需求内容」仅为「详见」/空/极短 → 以**有效附件正文**作为需求背景/内容原文来源，直接粘贴不改写。
- 若 in-page 已有实质内容且存在有效附件 → 一/二章优先 in-page 原文；附件正文作「三、技术实现」细化依据。
- 不论哪种，文档末尾标注「本需求含附件《xxx》，已通过 kjptai downloadUrl 自动拉取并转 md 消化」。
- 无效/冗余附件不参与一/二/三章内容来源，仅标注忽略。

## 五、多附件与缺失处理
- **多附件**：逐一对每份做「有效性判定」，有效附件分别纳入对应模块；无效附件统一标注忽略。伞型大需求建议在评审纪要「业务关注点」标注「建议按子需求拆解排期」。
- **附件缺失/拉取失败**：不中断，提示用户「需求 [编号] 含附件但自动拉取失败，分析基于已有文本进行，附件待补充」；在评审纪要「需求补充说明」追加提示。
- **重复分析**：先读本地附件目录已有附件，与 kjptai 附件合并按本节规则处理，不重复下载。
