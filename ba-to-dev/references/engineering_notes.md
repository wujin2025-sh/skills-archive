## ⚡ 性能优化（2026-11-05 R2610290057 实测固化）

> **目标**：单需求全流程分析控制在 **5-8 分钟**（R2610290057 观测基线 15-20 分钟；按区间中值折算缩短约 60%–75%，该折算为估算，未做批量计时留痕）。
> **耗时排序**：CBM 串行检索 >> 数据库直连失败重试 > openviking 多轮往返 ≈ 无谓方向检索。

| 优先级 | 瓶颈 | 实测 | 对策 |
|--------|------|------|------|
| P0 | CBM `search_graph` 多次**串行** | 单次 30-120s、约 5-8 次 | ① 多关键词**并行**发起（同一批独立检索并行，勿串行等待）；② 按改造主题**合并查询**（如「行权融资还款」一次命中 stkOrder/gqjl 全部函数，勿逐函数反复搜）；命中核心改造点即止，细节由源码 grep 秒级补位 |
| P0 | 数据库直连失败重试 | 2 次全失败（TLS 握手/权限受限）纯浪费 | **直连前置预判**：非白名单库/无可用凭据**直接跳过**，表结构以代码引用为准；失败一次即熔断不再重试（本次 jzjy-sit64/jzqs 教训） |
| P1 | openviking 多轮 find/list/read 往返 | 单次 2-4s × 6-10 次 | 一次路由定位（交易所规则 vs 既有需求 vs 用例）后**精准 read 命中文件**，检索词预判命中，减少全量 find |
| P1 | 无谓方向检索（如行权融资强关联两融） | 若干次 | 三域检索**只查需求原文实涉业务**；原文未提及的相关业务**一律不检索**，严禁按「可能相关」扩检索（本次教训：两融方向全为低价值输入） |

**执行纪律（与既有 P0 门禁联动）**：
1. **检索并行化**：同一批独立的 search_graph / openviking 调用并行发起，禁止串行等待；
2. **溯源收敛**：定位到表名/字段/函数/功能号即转落盘（联动 Step 2「溯源收敛门禁」），CBM 单主题至多 2-3 次查询；
3. **失败熔断**：数据库直连/图谱接口异常一次即熔断，转代码引用/源码 grep 兜底，不重试、不阻塞落盘；
4. **检索纪律**：只查需求实涉业务方向，杜绝「可能相关」的扩展检索。

## 🎯 检索命中率优化（2026-11-09 沉淀，2026-11-19 实测复核）

> **目标**：减少 fallback 往返。**主动首查**（先用最高命中率方法）替代**被动 fallback**（0 命中后才走兜底链）。

### 执行纪律

1. **首查命中率优先**：每个检索域**首次查询即用最高命中率方法**，不走默认低命中率路径再 fallback：
   - CBM 首查用代码符号（§8 预映射），不用业务中文；
   - OpenViking 首查用 2-3 近义词并行 find，不用单一概念；
   - 本地 MD 首查用 Glob+Grep，L3 兜底自动追加；
   - 接口查询首查用 **fwzl-mcp（服务治理平台）**，本地库仅兜底；
2. **并行替代串行**：同一批独立的检索调用（多近义词 find / 多符号 search_graph / 多概念反查）**并行发起**，禁止串行等待；
3. **命中率自检**：每个检索域完成后快速自检——首查命中即进入下一域；首查 0 命中才走 fallback 链（≤2 轮）；fallback 全未命中按熔断标注后继续，**不阻塞落盘**；
4. **预映射字典持续积累**：每次溯源定位到新代码符号后，自动追加到 `graph_lookup.md` §8 预映射字典，供后续需求首查复用；
5. **文档属性双写（本地域唯一真实短板）**：落盘时**文件名需求号 + front matter `req_id` 必须双写**；发现历史文件缺号（无文件名号、无 req_id、正文亦无号）时在第四章审计标注「该文档对需求号检索隐身，建议补号」。实测证明本地检索瓶颈不在算法，在属性缺失——补 9 份无号文档比优化检索策略收益更大。

## 🚀 分层并行设计依据与对照（2026-11-12 定稿，2026-11-21 从 SKILL.md 迁入）

### 三域依赖与最优顺序

| 依赖 | 强度 | 说明 |
|------|------|------|
| 代码域(CBM) → 数据库域(dbq) | **强（必须）** | db 域是交叉验证，须先有 CBM 定位出的表名/字段，blind 查库无效。**数据库域必然压轴** |
| 业务规则域(openviking) → 代码域(CBM) | **软（该用）** | openviking 给业务口径（阈值/边界/触发条件）→ 反推更准的代码符号，提升 CBM 首查命中率 |
| 业务规则域 → 数据库域 | 间接 | 规则口径可指导"查哪个字段/参数"，非前置 |
| 代码域 → 业务规则域 | 无 | 符号检索不需规则先行 |

> **实测教训（R2611120045，2026-11-12）**：曾因 CBM 定位到功能号即"溯源收敛"直接落盘，**无声跳过了 openviking**，而该需求"维保过低触发平仓限制"正是需要业务规则印证的——事后补查 openviking 命中 130%/110% 强平规则（R2607070027）。根因=把「代码域收敛」混同「三域完成」，落盘前必须走三域打勾检查。
