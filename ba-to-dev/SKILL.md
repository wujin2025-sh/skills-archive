# BA-to-Dev: 业务需求转研发文档工作流

> **角色**：资深券商 IT 业务需求分析师 (BA)  
> **目标**：消除歧义、细化边界、提炼规则，产出可直接指导研发与测试的结构化 Markdown 规格说明书。

---

## 🧭 意图路由（最高优先级，2026-11-20 新增，借鉴 universal-requirement-review）

**一进来先判意图，再决定走哪条轨道**——避免把「想查询/想复用/想下发联动」误当「重新生成文档」执行，杜绝方向错误。按如下固定顺序判定（命中即分流，只进一条轨道，不再混跑后续步骤）：

| 意图 | 判定信号 | 行为（轨道） |
| :-- | :-- | :-- |
| `CONFIG_MANAGEMENT` | 用户说「配置/初始化/升级/改偏好」，或引到技能的配置/设置 | 处理配置，**不进入需求分析** |
| `FORCE_REFRESH` | 指令显式带 `--force` / `--remote` | 拉平台 → 100% 覆盖一二章 → 重跑三域 → 落盘 |
| `LOCAL_REUSE` | 给需求号 / URL、**无 `--force`**、本地 L1~L3 命中 | **0 秒读本地 MD**，增量审查，不查平台不建新文件 |
| `GENERATE_DOC` | 给原文 / URL / 明确说「生成研发文档/需求转研发/消歧」 | 全流程分析落盘 |
| `DOWNSTREAM_LINK` | 说「拆 Story / 评审 / 登记价值量 / 改排期 / 标签 / 上云」 | 直接引导对应下游 skill，不重排 BA 主流程 |

**硬性纪律**：
1. **字面 `--force`/`--remote` 才是强制刷新，绝不因"用户提了需求号"就默认刷新**；
2. **本地命中且无 `--force` → 一律 0 秒复用**，即便用户语气像是在"要文档"——增量审查即可，不触碰平台与文件重建；
3. 判定歧义时向用户确认一句（≤3 问，须给选项），不猜。
4. 该路由只决定"走哪条轨道"，进入轨道后 `LOCAL_REUSE`/`GENERATE_DOC`/`FORCE_REFRESH` 均复用下方「极速工作流」的 Step 1~4。

## 🔭 能力按角色抽象与证据四态（2026-11-20 初稿，借鉴 universal-requirement-review）

**能力抽象成三个角色**，SKILL 流程只认角色、靠配置映射到具体源——换知识库/代码库不需改流程，只改配置：

| 角色 | 当前实现源 | 命令/能力 |
| :-- | :-- | :-- |
| `business_rule` 业务规则 | openviking | `openviking_mcp.py find/glob/read` |
| `code_lookup` 代码 | codebase-memory-mcp | `search_graph` / `get_code_snippet` / `trace_path` |
| `data_verify` 数据 | database | `dbq <profile>` |

**证据四态（每个源独立记录，未启用/查无/失败严格区分）**：

| 状态 | 含义 | ba-to-dev 落点 |
| :-- | :-- | :-- |
| `checked_with_evidence` | 已调用并取到相关证据 | 🟢 已实证 / 🟡 可追溯 |
| `checked_no_relevant_result` | 调用成功但范围内无相关结果 | 三章/四章标注「该域已检索、无相关」，**≠ 能力不存在** |
| `unavailable` | 已启用但源/权限/调用当前不可用 | 标注「该源暂不可用（失败原因）」，继续用同角色其他源 |
| `not_enabled` | 未启用 / 绑定停用，本次未调用 | 标注「该源未启用」，不视为故障，不伪造证据 |

**融合既有证据三态（🟢🟡🔴）**：合成「结论可信度（🟢/🟡/🔴）」+「源可用性（上表四态）」双维留痕——既说结论可不可信，也说"当时这个源是没查 / 查无 / 坏掉"，杜绝把源失效静默当成已检索。落地为第三章溯源表与四章审计的可选「证据覆盖」行（**本稿未改既有 P0 检索逻辑，仅新增留痕约定，供渐进采用**）。

## ⚡ 极速工作流 (Zero-Latency Workflow)

```mermaid
graph TD
    A[输入需求号 / URL / 原文] --> B{本地检索 /100_Projects/需求分析/<br>Glob + req_id Grep}
    B -->|已存在本地文档 & 无 --force| C[⚡ 0秒极速复用本地 MD<br>绝不查询科技平台 / 绝不新建文件]
    B -->|未命中 或 携带 --force| D[调用 gtht-req-query 拉取平台详情]
    C --> E[增量审查 / 架构细化 / 评审纪要]
    D --> E
    E --> F[自动运行 validate_ba_md.py --fix<br>完成格式自动纠偏与互斥门禁校验]
    F --> G[落地标准 Markdown & 引导下游工具链]
```

## 🚀 分层并行执行协议（2026-11-12 定稿：openviking 抢先半步 + db 压轴）

> **目标**：三域检索从串行 sum(耗时) 降至并行 max(耗时)，同时让业务规则口径**抢先半步**校准代码检索方向，提升 CBM 首查命中率。单需求全流程目标 **3-5 分钟**（2026-11-10 基线 5-8 分钟）。
> **与既有章节关系**：本节是「⚡ 性能优化」与「🎯 检索命中率优化」的**执行编排层**——前者定义瓶颈与对策，后者定义首查命中率策略，本节定义**何时发起、哪些并行、哪些等待**。

### 三域依赖与最优顺序（设计依据）

| 依赖 | 强度 | 说明 |
|------|------|------|
| 代码域(CBM) → 数据库域(dbq) | **强（必须）** | db 域是**交叉验证**，须先有 CBM 定位出的**表名/字段**才有东西可查，blind 查库无效。**数据库域必然压轴** |
| 业务规则域(openviking) → 代码域(CBM) | **软（该用）** | openviking 给业务口径（阈值/边界/触发条件）→ 可**反推更准的代码符号**，提升 CBM 首查命中率。**openviking 天然抢先半步** |
| 业务规则域(openviking) → 数据库域(dbq) | 间接 | 规则口径可指导"查哪个字段/参数"，非前置 |
| 代码域(CBM) → 业务规则域(openviking) | 无 | 符号检索不需规则先行 |

**一句话**：业务规则域=方向盘（最先出结论引路）、代码域=发动机（居中）、数据库域=质检仪（压轴验证）。唯一硬顺序是 code→db。

### 执行波次（分层并行）

| 层 | 检索动作 | 依赖 | 并行粒度 |
|----|----------|------|----------|
| **第 0 层** | 需求原文解析 + 本地三级检索（L1/L2/L3） | 无，先行 | 三级并行 |
| **第 1 层** | **openviking find（2-3 近义词）** + CBM search_graph（预映射符号）+ 接口查询 + 需求依赖反查 | 无 | **三域并行发枪**；近义词间并行 + 跨系统跨符号并行 |
| **第 1.5 层（回灌/软协作）** | openviking `find`（粗筛秒回）冒头即**回灌校准 CBM 检索词**（业务语义→换英文符号再查） | 第 1 层 openviking find | 不等完成，先冒头即触发 |
| **第 2 层** | openviking `read` 规则正文 + **CBM 0 命中→用 openviking 业务词回灌→grep 源码兜底** + CBM 定位表名→触发 dbq | 第 1 层结果 | 命中文件并行 read / 多系统 dbq 并行 |
| **第 3 层（压轴）** | **数据库交叉验证 dbq**（表结构/字典/参数当前值；code→db 硬链） | 第 1/2 层 CBM 表名 | 多系统 dbq 并行 |

### 并行与顺序规则

1. **业务规则域抢先半步**：`openviking find`（秒回粗筛）与 CBM **同时发枪**，但 openviking 先冒头的语义**立即回灌**校准 CBM 检索词——既省时又不牺牲命中率（解决纯并行时 CBM 首查命中低的痛点）；
2. **openviking→CBM 软协作**：CBM 0 命中时**必须**用 openviking 业务词反推英文符号换词重试 + grep 兜底，禁止直接判无图谱（P0 #12）；
3. **db 压轴（唯一硬顺序）**：`dbq` 必须有 CBM 表名后才发，**严禁 blind 查库**；纯报错提示/纯 UI 类无表结构变化需求按 `显式跳过标准` 标注跳过；
4. **跨域并行**：第 1 层三域同时发起，不等任一域完成才启动另一域；
5. **跨系统并行**：CBM 多系统（jzjy/dys/jzqs/grc/cszx）search_graph **全部同时发起**；多系统 dbq 并行；
6. **同域多词并行**：openviking 多近义词 find、CBM 多代码符号、接口多接口号**同时发起**；
7. **熔断不阻塞**：任一域失败/超时按既有熔断（P0 #16/#18），不影响其它域继续并行；
8. **`--force` 路径并行**：拉取平台详情后，**骨架生成**（extract_demand.py）与**三域检索（第 1 层）同时启动**——三域依赖需求原文（已随平台详情返回），不依赖骨架文件。

### 显式跳过标准（三域任一跳过必须留痕，禁止静默略过）

> **落地门禁（P0）**：跳过的域必须在文档显式标注「此域因 [理由] 作选择性跳过」；未标注跳过=默认已检索。

| 域 | 允许跳过的唯一标准 |
|----|-------------------|
| openviking 业务规则 | 需求纯 UI / 纯技术重构，**无任何业务规则/阈值/口径语义**（如"按钮样式调整"）才可跳；凡涉「维保/强平/担保/权限/还款/质押/回购」等有业务语义的词**必须检索** |
| 数据库 dbq | **无新增/修改表结构/字段/参数**才可跳（如纯报错提示类）；跳时文档写明「该域因无表结构变化作选择性跳过」 |
| 代码域 CBM | 仅 `djgl/ssjs/jzyy` 无图谱系统可跳（P0 #12），其余必做 |

> **实测教训（R2611120045，2026-11-12）**：曾因 CBM 定位到功能号即"溯源收敛"直接落盘，**无声跳过了 openviking**（未显式评估），而该需求"维保过低触发平仓限制"正是需要业务规则印证的——事后补查 openviking 命中 130%/110% 强平规则（R2607070027）。根因=把「代码域收敛」混同「三域完成」，且「报错提示类需求=无业务规则」的主观低估。落盘前必须走三域打勾检查（见 Step 3）。
