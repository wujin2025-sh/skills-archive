# 需求原型

把用户给出的业务材料变成可实际操作的产品原型。外观与交互都要完成；项目规则由本次材料决定，不由模板或角色印象补造。

## 读什么，怎样判断

1. 读取用户这轮指定的文件。首次调用时同时读取 [视觉规范](references/视觉规范.md) 和 [界面基础样式](assets/workbench.css)。相对路径以本 Skill 所在目录为基准。不要为了找更多信息遍历整个工作区或读取后续轮次资料。
2. 用三五句话说明：解决什么问题、谁会使用、这轮要跑通哪条操作、有哪些明确约束。区分材料事实、用户本轮选择、尚未确定的演示假设。
3. 新的项目说明若明确调整了旧草稿，按新说明迭代并指出变化；两份正式规则有实质冲突且无法判断时，只问影响继续制作的那个问题。
4. 材料不足时，用最小、明确标注的演示假设先做可操作版本。只有核心流程确实无法判断才提问；不要一次提出十几个问题，也不从团队人物档案推断业务用户的权限。

## 先形成清楚的产品界面

- 读视觉规范，用基础样式中的颜色、字阶、间距、边框与反馈方式；可按业务调整布局。保持有秩序的列表、稳定的操作位置、明确的选中状态与精致的详情面板。
- 首屏服务当前任务：让人迅速找到自己的记录和下一步动作。不做营销大图、无意义的统计卡、装饰性仪表盘或与任务无关的功能入口。
- 默认以中文呈现；文件名、按钮、状态和字段使用项目材料里的词。金额、状态、人员、数量、期限等业务内容不得从视觉样例继承。
- 保持标题、正文、辅助信息层次分明；主按钮只突出当前主要动作。统一图标笔画、圆角和控件高度。需要图标时用少量内嵌 SVG；不依赖远程图标或字体。
- 迭代时保留已有视觉系统，除非新增要求确实需要改变。上下文的作用应体现在字段、流程、数据与范围上，不能把换颜色当作满足业务要求。

## 真正跑通交互

- 直接交付 HTML，CSS、JavaScript 与模拟数据内置。把 `workbench.css` 的必要内容嵌入 `<style>`，不要让最终文件依赖 Skill 文件夹、网络、CDN、npm、服务端或 API 密钥。无需为此任务安装框架。
- 所有看起来可操作的控件都应产生合理结果；没有做的功能不放假按钮。实现与本次流程有关的输入、校验、提交、查询、详情和状态反馈。
- 有角色或数据范围要求时，范围变化同时作用于列表、计数、搜索、详情和可用操作。切换后关闭已不在当前范围内的详情。原型里的身份切换标为“演示身份”，不冒充正式登录或服务端权限。
- 表单要处理空白输入、字段错误和成功反馈。报错保留已填内容，成功后新增记录应能被找到；用户内容用安全的文本方式渲染。
- 状态变化必须符合本次材料的规则，并同步相关列表、详情、计数与下一步提示。不虚构审批、通知、后台或材料明确排除的功能。
- 支持键盘操作、可见焦点、表单标签、Escape 关闭弹层、关闭后焦点返回；反馈使用可读文字。浏览器可用时用原生 `dialog` 处理模态与焦点。
- 以普通笔记本窗口和窄屏检查布局；长中文、无结果、空列表也要可读。页面主体不能横向溢出。
- 若使用本地保存，选择不会与旧版本或其他演示混淆的存储键，并处理存储不可用的情况。保留前一版文件，不把旧数据无声带入新项目规则。

## 交付前验证

有浏览器工具时，实际打开生成的 HTML，至少走通用户核心操作、一个失败输入、一个状态或角色变化，并检查控制台错误。不要只做语法检查就写“已验证”。根据项目要求增加必要检查。

自测使用隔离的浏览器数据，不能把测试新增、改状态后的数据留成用户初次打开的默认内容。项目指定初始记录时，交付首次打开须仍是该批记录；用户之后的操作正常保留。

没有浏览器工具时，做可执行的静态检查，并明确哪些交互尚待用户点击验证。不要编造截图或通过记录。发现问题先修复，再重走受影响的操作。

默认只交付用户指定的 HTML。保留上一版，返回可打开的位置、此次读了哪些材料、三项以内的主要变化，以及实际检查结果。除非用户要求，不生成额外说明书、汇报文档或安装指南。
