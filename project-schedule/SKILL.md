# 项目进度表生成器

## Overview

该 Skill 能够批量、并行地对多个需求编号（如 R2603130062 R2603110056）进行详细查询，从金融科技平台提取所有关联的 Story 状态、各系统负责人及交付排期，自动生成格式美化、带有需求编号单元格合并的项目进度跟踪表。支持输出为自包含的 HTML 表格文件以及 Markdown 文本。

## When to Use

- 用户提供了多个需求编号，要求整理一份统一的项目进度表用于邮件发送或干系人汇报。
- 触发词：进度表、项目进度、批量查询、生成进度表、合并表格。

## Usage

执行脚本，传入一个或多个以空格分隔的需求编号或史诗编号：

```bash
python3 scripts/project_schedule_generate.py <需求ID_或_史诗ID_1> <需求ID_或_史诗ID_2> ... [--project 项目名称] [--output_html html路径] [--output_md md路径]
```

### 实际结束时间自动抓取（推荐，替代硬编码）

大宽表缓存**不含** Story 实际结束字段（全 None），【实际结束】列数据源为平台 **Story 详情页「Story 一生」卡片**。已提供自动抓取脚本，抓取结果写入 `scripts/story_actual_end_cache.json`，生成排期表时自动加载合并（优先级：人工硬编码 `STORY_ACTUAL_END_MAP` > 自动缓存 > 平台缓存字段 > `--`）：

```bash
# 抓取史诗下所有 Story 的实际结束时间
python3 scripts/fetch_story_actual_end.py --epic E2603040001
# 抓取指定需求下 Story
python3 scripts/fetch_story_actual_end.py --demand R2609080068 R2607090114
# 全量刷新（覆盖缓存中已有条目）
python3 scripts/fetch_story_actual_end.py --epic E2603040001 --force
```

- 取数规则严格对齐「Story 一生」：开发实际结束 → `开发实际结束时间`；SIT → `SIT自测实际结束时间`；UAT → `UAT自测实际结束时间`。
- 关键 URL：`/kjpt/StoryManage/storyDetail?storyNo={R格式storyNo}`（storyNo 取大宽表缓存 `storyNo`/`dataUniqueNo` 字段，如 `R2410140070-1`，**非 S 编号**）。
- 幂等合并：默认仅更新成功抓取到的条目，不覆盖已有值；`--force` 全量刷新。
- 自动过滤已终止 Story（状态含「终止」）。

### 参数说明

- **需求ID/史诗ID**（至少一个）：以空格分隔的需求编号（如 R2603130062）或史诗编号（如 PG202204-0236）列表。如果传入史诗编号，系统将自动连接大宽表并提取出该史诗下所有关联的需求编号。
- `--project`：项目名称（默认："交易结算核心历史数据及接口迁移项目"）
- `--output_html`：生成的 HTML 表格保存路径（默认：`/Volumes/Macintosh HD_Data/obsidian/100_Projects/进度跟踪/{日期}-进度-{项目名称}.html`）
- `--output_md`：生成的 Markdown 表格保存路径（默认：`/Volumes/Macintosh HD_Data/obsidian/100_Projects/进度跟踪/{日期}-进度-{项目名称}.md`）
- `--send-mail` / `--mail` / `--draft` / **“发邮件”指令**：严格提取 HTML 跟踪表中真正涉及的所有人员（开发经办人、SIT经办人、UAT经办人、需求提出人、业务验收人，绝不引入无关人员）作为收件人，无头模式将 HTML 进度跟踪表起草存入 Coremail 草稿箱（`草稿箱`）。
- **固定抄送（CC）**：发邮件时抄送人固定为 `刘勇明、周尤珠`（脚本内已硬编码，无需额外参数）。
- **已终止 Story 过滤**：状态为 `终止`（含 `已终止`）的 Story 一律从进度表、逾期/未排期预警及收件人提取中彻底剔除，不展示、不提醒。
- **统一输出目录**：HTML 与 Markdown 文件默认均输出到 `/Volumes/Macintosh HD_Data/obsidian/100_Projects/进度跟踪/` 目录下，文件名为 `{日期}-进度-{项目名称}.html` / `.md`。

### 环境要求与凭证配置

- **凭据配置**：其他用户使用前，可以在 Skill 目录下的 `config.json` 中配置自己的平台登录 `username`（明文工号）和密码。
  - **明文配置**：可以直接在 `config.json` 里的 `"password"` 字段配置您的明文密码。
  - **加密配置 (推荐)**：为了防止分享/复制 Skill 给别人使用时泄漏密码，可以运行以下命令交互式输入并加密密码：
    ```bash
    python scripts/encrypt_pwd.py
    ```
    它会将您的密码加密为密文写入 `password_encrypted` 字段，并清除明文 `password` 字段。
- Python 虚拟环境 `.venv/` 中需安装 `playwright`
- 项目根目录下存在公用的 session 文件 `.fintech_session.json`
- 并行最大并发数默认不限制（通过 asyncio.gather 并行执行）

### 核心列与过滤规则说明

1. **经办人姓名精准提取与动态流程节点提取**：
   - **有效经办人提取**：优先通过中文正则匹配提取干净姓名（如 `宁秀芳-114780` -> `宁秀芳`，`邢航源-CP_xinghangyuan` -> `邢航源`），绝不因账号后缀/前缀格式剥离或误清空有效的开发与测试经办人；仅在整项字符串完全无对应人名时记为 `/`。
   - **节点过滤规则**：严格拦截并忽略 `Story 创建` 与 `Story 待处理` 节点，仅解析扫描 `开发待排期`、`待开发`、`开发中`、`开发完成`、`SIT测试`、`UAT自测` 节点的人员。

2. **23 列高保真表格结构与【预计/实际结束】严格提取引擎**：
   - 在 **💻 开发相关**、**🧪 SIT 测试**、**🔍 UAT 自测** 三个核心阶段的 **【预计结束】** 右侧分别新增 **【实际结束】** 列，表格完整展示 23 列列要素。
   - **【预计结束时间】各阶段提取法则**：
     - **开发相关**：**预计结束** 严格取自 **Story 详情 -> 评估 / 基本信息 : 开发预计结束时间**（`devAssessDateEnd` / `storyItDuedate`）。
     - **SIT 测试**：**预计结束** 严格取自 **Story 详情 -> 评估 / 测试信息 : SIT测试预计结束时间**（`sitTestAssessDateEnd` / `testAssessDateEnd`）。
     - **UAT 自测**：**预计结束** 严格取自 **Story 详情 -> 评估 / 测试信息 : UAT自测预计结束时间**（`uatTestAssessDateEnd`）。
   - **【实际结束时间】各阶段提取法则（严格对齐 Story 一生）**：
     - **开发相关**：**实际结束** 严格取自 **Story 一生 : 开发实际结束时间**（`devFactEndDate` / `devActualDate` / `devFinishTime`）。
     - **SIT 测试**：**实际结束** 严格取自 **Story 一生 : SIT自测实际结束时间**（`sitFactEndDate` / `sitActualDate` / `sitFinishTime`）。
     - **UAT 自测**：**实际结束** 严格取自 **Story 一生 : UAT自测实际结束时间**（`uatFactEndDate` / `uatActualDate` / `uatFinishTime`）。
   - **绝对约束法则**：
     1. 若平台 `Story 一生` 中对应环节尚未生成或单独录入实际完成时间，一律真实如实展示为 `--`，绝对禁止借用预计结束时间假冒兜底！
     2. 绝不使用版本计划发布/上线交付日期（如 `largeDeliverDate` / `smallDeliverDate` / `planProdLineDate`）作为阶段实际完成时间。
     3. 绝不跨阶段互相挪用预计或实际完成时间。
   - 表格列名 **`业务验收结果`** 正式重命名为 **`验收状态`**。
   - 三大核心人员/状态字段精确提取规范（完全对齐平台 **Story 详情**，严格独立 Story 级别提取）：
     - **原始需求提出人**：严格取自 **Story 详情 - 基本信息 : 原始需求提出人**（`originalRequester`），隔离平台需求级经办人干扰。
     - **业务验收人**：严格取自 **Story 详情 - 业务与设计 : 业务验收人**（`businessAcceptorName` / `storyBusAcceptor`），**绝对禁止降级退化至需求级 (Demand-level) 连体或拼接字符串**。
     - **验收状态**：严格取自 **Story 详情 - 业务与设计 : 业务验收结果**（`storyBusName` / `storyResult` / `storyBusResult` / `isHaveBus` -> `无需业务验收` | `待业务验收` | `已验收`）。

3. **各阶段标准状态规范**：
   - 彻底废除“正常”或“未排期”等模糊统称，严格映射为规范标准阶段状态：
     - **开发状态**：`已完成` | `待开发` | `开发中` | `待排期`
     - **SIT 状态**：`已完成` | `待自测` | `自测中` | `自测待排期` | `--`
     - **UAT 状态**：`已完成` | `待自测` | `自测中` | `自测待排期` | `--`

4. **【逾期 N 天】精准计算与展示法则 (开发、SIT、UAT 各阶段独立优化)**：
   - **核心判定准则**：针对 **💻 开发相关**、**🧪 SIT 测试**、**🔍 UAT 自测** 各自阶段独立计算。仅当该阶段存在 **`实际结束`** 日期，且 **`实际结束 > 预计结束`** 时，计算并展示 `逾期N天`（精准公式：`逾期天数 = 实际结束日期 - 预计结束日期`）。
   - **否则不填 / 不展示**：若未录入/无实际结束日期（环节推进中），或 `实际结束日期 <= 预计结束日期`（按期或提前完成），一律**不填/不展示逾期天数**。
   - **时间联动补全**：若环节状态为 `已完成` 且具有实际结束日期，但初始评估计划日期为空，自动以实际结束日期补齐预计结束，确保已完成环节时间数据 100% 完整。

5. **【计划生产排期】直读大宽表法则与自动命名**：
   - **直读大宽表（不硬编码）**：【计划生产排期】统一从需求大宽表缓存中 Story 的 `planProdLineDate` 字段实时读取，绝不使用任何硬编码映射覆盖。当通过 `adjust-plandate` 等工具修改排期后，大宽表缓存会自动刷新，进度表随之同步更新。
   - **史诗名称自动命名法则**：系统解析史诗编号后，自动提取史诗真实名称（如 `CX-业务-QFII两融-二期`），自动命名输出产物：`{日期}-进度-{史诗名称}.html` 与 `{日期}-进度-{史诗名称}.md`。

6. **全行内 CSS 样式 (Inline CSS) 与高保真邮件起草**：
   - HTML 报表中的所有元素（表头 `#1e40af` 蓝色块、灰阶列头、胶囊徽章、卡片阴影容器等）均注入 100% 显式行内 `style="..."` 属性，彻底防止 Webmail / Coremail 邮件客户端剥离 CSS。

7. **全量收件人提取、无工号/外包过滤与 Coremail 自动存草稿箱**：
   - 运行 `--send-mail` 或执行“发邮件”指令时，系统精准提取 HTML 表格中涉及的 **原始需求提出人**、**业务验收人** 及 **开发/SIT/UAT 经办人**。
   - **无工号/外包账号过滤规则**：若经办人无标准员工工号（如外包账号 `邢航源-CP_xinghangyuan`，含 `CP_` 前缀或无 5-6 位数字工号），在起草邮件时收件人不填写该人员，彻底避免 Coremail 出现无法匹配解析的红色标记。
   - **重名邮箱定向映射规则**：在 `《人员部门对应关系表》.csv` 中增加可选 `邮箱` 列。对于无重名人员，`邮箱` 列保持留空（自动输入纯中文姓名）；仅对于有同名重名的特定人员（如 `丁伟`），在 CSV 的 `邮箱` 列中填入具体邮箱账号（如 `dingwei2@gtht.com`）。系统在起草存草稿时会自动读取该映射，将重名人员自动替换为精确邮箱地址写入，实现绝对零歧义匹配。
   - 自动在无头模式下把包含了行内样式正文、最新提醒 Block 以及 HTML 表格附件（`--attachments`）的邮件起草存入 Coremail **草稿箱**。

8. **史诗编号跨行合并 (Continuous Rowspan)**：
   - 所有需求（包括 0 个 Story 的无关联需求）均继承目标 Epic 编号，在 HTML 和 Markdown 报表中保证首列史诗编号单元格整块全行无缝跨行合并。

9. **未完成 Task 当前阶段责任人精准 @ 强提醒规则**：
   - 邮件正文底部动态追加【推进提醒】Block：凡已完成或已上线的 Story / 环节 **自动跳过、不进行提醒**。
   - 针对未完成的 Task，精准锁定其 **当前活跃阶段**（开发 / SIT测试 / UAT自测 / 业务验收），并在正文底部列出 Task 编号、对应系统及 **`@当前阶段责任人`** 强提醒。
   - **UAT 完成阶段联动**：若 Task 的 UAT 状态已标记为 `✅ 已完成` 且进入业务验收阶段，系统会自动 **`@原始提出人`** 及 **`@业务验收人`** 提醒推进业务验收！

10. **极速缓存与 Obsidian 同步**：
    - Playwright 首次提取后自动结构化回写至 `.table_cache.json` 缓存，后续再次查询/导出实现 `< 2.5 秒` 极速秒出。
    - 自动同步写入 Obsidian 目录：`/Volumes/Macintosh HD_Data/obsidian/100_Projects/进度跟踪/`。

11. **空白行与占位 Story 智能过滤法则**：
    - 若需求下已存在真实的关联 Story 记录（如 `R2603250136` 包含 `S2604130029` / `S2604130030` / `S2606030083`），系统将自动彻底过滤剔除由数据缓存残留产生的空白占位/无关联 Story 行，保证表格洁净无任何多余空行。

12. **【实际结束时间】严格对齐 Story 一生法则**：
    - **开发相关实际结束**：**严格取自 Story 一生 : 开发实际结束时间**（`devFactEndDate` / `devActualDate` / `devFinishTime`）。
    - **SIT测试实际结束**：**严格取自 Story 一生 : SIT自测实际结束时间**（`sitFactEndDate` / `sitActualDate` / `sitFinishTime`）。
    - **UAT自测实际结束**：**严格取自 Story 一生 : UAT自测实际结束时间**（`uatFactEndDate` / `uatActualDate` / `uatFinishTime`）。
    - **真实性约束**：若平台 `Story 一生` 中对应环节尚未生成或录入实际完成时间戳，一律真实如实展示为 `--`，绝对禁止借用预计结束时间假冒兜底。

13. **特异账号前缀与外包经办人姓名强还原法则 (`CP_` 等)**：
    - 在解析开发/SIT/UAT 经办人时，针对带有 `CP_` 等特异账号前缀或格式的经办人（如 `devHeaderId: CP_xinghangyuan` 对应 `邢航源`），系统优先扫描并提取 `devHeaderName` / `devManagePerson` 汉字文本，自动精准还原为纯中文姓名，彻底防止经办人字段因账号格式而被误记为 `/`。
