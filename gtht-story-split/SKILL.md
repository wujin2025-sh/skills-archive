# 国泰海通 Story 自动化拆分技能 (gtht-story-split)

自动按需求评审结论或 `ba-to-dev` 产出的需求 Markdown 文档，在国泰海通科技平台（fintech.gtht.com.cn）中为目标系统拆分所属 Story，并自动发起技术评估。

> ⚡ **性能与可靠性**：
> - **API 直连（默认）**：优先打后端 REST API 完成 Story 拆分与属性填充，**≤1-2s/系统**，免浏览器渲染；
> - **UI 自动化（兜底）**：指定 `--browser` 参数或 API 异常时，自动切至 Playwright 条件等待渲染进行表单操作。

## 🚀 两种主要使用模式

### 模式一：`ba-to-dev` 需求文档自动化联动（最常用推荐）

当用户完成 `ba-to-dev` 需求分析并生成 Markdown 文档后，或用户说「拆分Story」、「对刚才的需求拆Story」时：

1. **自动定位需求文档**：优先读取当前对话或 `/Volumes/Macintosh HD_Data/obsidian/100_Projects/需求分析/` 目录下最新修改的需求 Markdown 文档。
2. **要素提取规则**：
   * **`req_id`**：读取 Front Matter `req_id: R26xxxxxxx` 或 Markdown 标题/链接中的需求编号；
   * **改造系统 (改造类)**：提取 `评审纪要 ➔ 2. 改造范围` 列出的系统（拆分出的 Story 名称不加前缀）；
   * **联测系统 (配合测试类)**：提取 `评审纪要 ➔ 8. 联测涉及系统` 列出的外围系统（拆分出的 Story 名称自动强加 **`【配合测试】`** 前缀）；
   * **灰度影响 (`impact-grayscale`)**：提取 `评审纪要 ➔ 7. 灰度上线关注` 首行（`是` ➔ 填 `是`；`否` ➔ 填 `否`）；
   * **业务验收 (`need-biz-accept`)**：提取需求提交人部门，若非「技术研发部」则判断为 `是`，并设置业务验收人为需求提交人。
3. **自动执行拆分脚本**：
   ```bash
   python3 "$SCRIPT" <req_id> \
       --systems "改造系统A:改造,外围系统B:配合测试" \
       --impact-grayscale <是|否> \
       --need-biz-accept <auto|是|否> \
       --biz-acceptor <auto|姓名>
   ```

---

### 模式二：命令行 / 对话参数化直接拆分

用户直接提供需求编号和涉及系统进行拆分：

```bash
# 示例：为 R2608100032 拆分集中清算（配合测试）和集中交易（改造）
python3 "$SCRIPT" R2608100032 \
    --systems "集中清算:配合测试,集中交易:改造,三方存管:配合测试" \
    --impact-grayscale 否 \
    --need-biz-accept auto \
    --biz-acceptor auto
```

#### 参数说明表

| 参数 | 必填 | 格式与说明 | 默认值 |
|---|---|---|---|
| `<req_id>` | **是** | 需求编号，如 `R2608100032` | - |
| `--systems` | **是** | 逗号分隔 `"系统名:类型"`，类型 ∈ `改造` \| `配合测试` | - |
| `--template-map` | 否 | 逗号分隔 `"系统名=模板名"`（系统名与模板名不一致时使用） | 空 |
| `--impact-grayscale` | 否 | 是否影响灰度升级：`是` \| `否`（跨系统接口变更选 `是`） | `否` |
| `--need-biz-accept` | 否 | 是否需要业务验收：`auto`（自动推断）\| `是` \| `否` | `auto` |
| `--biz-acceptor` | 否 | 业务验收人：`auto`（取需求提交人）\| `姓名` | `auto` |
| `--dry-run` | 否 | 只模拟打印 payload，不实际提交落库 | `False` |
| `--browser` | 否 | 强制走 Playwright 界面自动化进行填报（API 异常时使用） | `False` |

## 📋 Story 拆分业务处理规则

1. **已有 Story 跳过幂等**：
   拆分前自动查询需求下已有的 Story 列表。若目标系统已存在 Story，**直接跳过，绝不重复拆分**（每个系统最多拆分一个 Story）。
2. **套用系统模板 (`使用模板`)**：
   若平台提供目标系统的拆分模板（如 `集中清算`、`集中交易`、`三方存管`、`参数后台`），自动套用模板填充默认属性。
3. **复制父需求描述**：
   自动提取父需求的正文描述，填充至新建 Story 的描述字段中。
4. **【配合测试】名称前缀**：
   类型标注为 `配合测试` 的系统，自动在其 Story 名称最前方添加 `【配合测试】` 前缀（如 `【配合测试】集中清算系统改造...`）；改造类系统不加前缀。
5. **发起技术评估（收尾闭环）**：
   Story 拆分完成后，系统会自动在「所属Story」模块勾选本次新增拆分的所有 Story，并触发「发起技术评估」。
